# WaTools 全仓审查与优化规划

本轮审查基于 2026 年 10 月 2 日的仓库提交 `a213873`，覆盖插件安装与运行、官方插件、命令扫描与监听、平台 API、数据持久化、自动更新、依赖和发布流程。目标是为下一轮优化提供可拆分的缺陷清单、架构建议和验收条件。本轮只增加审查文档与验证材料，没有修改产品实现。

主要结论：当前代码可以构建，已有测试可以通过，但插件生命周期、持久化一致性和更新安装仍有需要优先修复的缺陷。下一轮应先保护用户数据和安装可靠性，再改插件加载机制，然后完善 SDK、平台能力和性能。插件隔离必须先明确可信模型；当前实现将插件视为用户主动安装的可信代码，不能把 iframe 或前端 package scope 描述为安全沙箱。

## 插件加载与本地数据

### R01 插件升级应保留数据并支持回滚

[installer.go](../internal/plugin/installer.go) 第 95 行通过 `UninstallPlugin` 替换旧版本；卸载删除目录和数据库记录，第 498 行附近再以 `Enabled: true`、`Storage: "{}"` 注册。安装相同或更高版本会丢失插件配置、存储、使用统计，并把原先禁用的插件重新启用。新包复制或数据库登记失败时，旧版本也已经被删除。

建议将安装目录与用户数据分离。新包先解压到独立 staging 目录，完整验证后切换版本目录；数据库更新保留 enabled、storage 和 usage，并为数据迁移设置 schemaVersion。失败恢复旧版本。旧 manifest 损坏时也需要允许修复安装，当前读取旧 manifest 失败会直接拒绝覆盖。

验收：覆盖安装与同版本重装保留数据；复制失败、磁盘满、数据库写入失败后旧版本可运行；禁用状态不变；坏包不影响已安装版本。

### R02 重新启用需要进入完整加载流程

[api/plugin.ts](../frontend/src/api/plugin.ts) 第 64 行只导入 enabled 插件，初始禁用插件的 entry 保持空数组。[pluginStore.ts](../frontend/src/stores/pluginStore.ts) 第 144 行的 toggle 只修改 enabled。探针中从启动禁用状态切换为启用，结果仍为 `entry: []`，因此不会产生可用命令。

建议用显式状态机维护 discovered、loading、ready、disabled、failed，启用操作等待加载完成后再发布 ready 状态。停用操作执行 dispose，并撤销宿主能力。管理页展示 enabled 与实际加载状态，避免把 enabled 等同于“已加载”。

### R03 插件升级需要版本化整个模块资源地址

[api/plugin.ts](../frontend/src/api/plugin.ts) 第 68 行使用稳定 URL 动态 import。包被覆盖后，相同 URL 的 ES module 仍来自当前 WebView 的模块缓存；点击刷新只是重新 import 同一模块，不能加载新版本代码。禁用也不会撤销模块顶层注册的定时器或事件。

建议使用不可变版本目录或内容哈希路径，例如 packageId、version、contentHash 共同标识资源。只给入口追加 query 不足以解决相对导入依赖的缓存，需要版本化整棵资源树。提供 activate、execute、deactivate、dispose 生命周期，明确更新时是否允许旧 UI 会话继续运行。

验收：同一会话升级后执行新代码；相对 import 也更新；停用后没有遗留监听器或后台任务。

### R04 坏插件应单独失败

[pkg/models/plugin.go](../pkg/models/plugin.go) 的 `GetFullInfo` 在 manifest 丢失或解析失败时返回 nil；后端列表保留该元素。[api/plugin.ts](../frontend/src/api/plugin.ts) 第 38 行直接访问 `plugin.packageId`，遇到 null 会使整个 getPlugins 失败。一个插件损坏可以导致所有插件不可用，并且管理页难以修复问题插件。

建议后端始终返回 packageId 与结构化状态，metadata 出错时保留可卸载的 failed 条目；前端逐项校验 null 和字段类型。运行入口加载超时或失败也要体现在插件状态中，目前错误仅写入 console。

### R09 后端状态需要快照与一致的锁策略

[internal/plugin/plugin.go](../internal/plugin/plugin.go) 的 storageMutex 仅覆盖 Storage API，`loadPlugins` 替换整个 pluginStates、`TogglePlugin` 修改状态、`GetPlugins` 序列化状态均不受该锁保护。并发安装、卸载、读取与存储写入可能产生 race 或读取过期对象。StorageSet 先修改内存再保存数据库，持久化失败后内存与磁盘不一致。

[internal/command/command.go](../internal/command/command.go) 第 158 行重建 applicationRunner，第 196 行执行时读取该 slice；现有 ApiMutex 只保护数据库加载，没有保护 runner 发布与执行。建议集中状态锁、返回不可变快照，或将相关操作串行化；先完成持久化再发布状态，并让更新失败可回滚。这里是静态识别的风险，现有 race 测试未覆盖这些交错场景。

### R18 UI 插件启动上下文应该固定到一次会话

[wa-plugin.tsx](../frontend/src/components/watools/wa-plugin.tsx) 的 URL effect 依赖 launchContext，iframe onLoad 又调用 clearInputValue。liveContext 随之改变，launchContext 重新解析或退回空上下文，effect 会生成新的时间戳 URL。正常持久化的 launchId 也可能因重新解析产生新对象而额外加载；sessionStorage 写入失败且传入图片等没有 seed 的场景可能丢失上下文。

建议在 launchId 或 packageId 与 entry 变化时固定初始上下文，通过一次 ready 握手传入；宿主清空输入不应改变会话身份和 iframe src。不要把大段输入继续复制到 URL。无效入口应给出错误与返回入口，当前永久展示 loading。

### R21 安装包处理需要独立临时目录与配额

[installer.go](../internal/plugin/installer.go) 第 44 行以 Unix 秒构建目录名，并用 MkdirAll 重用已存在目录。并发安装会共享解压空间与清理动作；本地预先放置的目录或符号链接也不在词法路径检查的保护范围内。解压循环没有文件数、展开总量、单文件大小和压缩比限制，关闭文件的错误也没有完整处理。

建议使用 `os.MkdirTemp`，限制展开字节数与文件数量，拒绝特殊文件及符号链接，逐层检查实际路径或使用受限目录句柄。现有 `ResolvePathWithinBase` 已拒绝 `..`、绝对路径、盘符等输入，本轮没有把普通字符串 Zip Slip 误判为未防护；剩余问题是共享目录、实际链接和资源用量。

### R25 用户数据应从缓存目录迁出

[config/config.go](../config/config.go) 的 ProjectCacheDir 被数据库、插件存储、安装包、热键和日志共同使用。系统缓存清理会同时影响用户配置、插件代码和业务数据。这是数据生命周期设计风险，不能依赖缓存目录长期保留。

建议 macOS 的长期数据使用 Application Support，Windows 使用明确的用户应用数据目录；缓存只保存可重建图标和下载暂存。迁移时先备份与校验，再切换路径，并提供导出、恢复与插件卸载后的数据保留规则。

## 命令与平台功能

### R05 应用统计转换遗漏字段

[pkg/db/conversion.go](../pkg/db/conversion.go) 第 12 行只调用 NewApplicationCommand，没有拷贝数据库 UsedCount 和 LastUsedAt。Go 探针把数据库的 usedCount 42 转换为 0、最近使用时间转换为 None。重启或命令刷新后统计归零；前端再从 0 增长并通过绝对值 UPDATE 回写，还会覆盖数据库中的历史累计值。

建议恢复字段映射，并优先由后端记录使用事件、执行增量累计。验收包括重启、watcher 刷新、应用改名后的累计次数与排序连续性。triggerId 也应由稳定应用 ID 构成，当前名称参与标识会使改名后的排序历史失联。

### R06 统计缓冲应确认快照而非清空整个集合

[pluginStore.ts](../frontend/src/stores/pluginStore.ts) 第 137 行和 [applicationCommandStore.ts](../frontend/src/stores/applicationCommandStore.ts) 的 flush 都在等待请求后直接清空 updateBuffer。请求期间新增的更新会被一起清掉。探针中第一笔写入期间发生第二次使用，usedCount 已为 2，但回写第一笔后 bufferSize 变为 0，第二笔不再落库。多个 flush 还可以并发写入不同的绝对计数。

此外，[internal/plugin/plugin.go](../internal/plugin/plugin.go) 的 UpdatePluginUsage 只更新数据库，没有更新内存中的 pluginStates。前端刷新列表仍可能得到旧计数，再次使用时覆盖较新统计。

建议采用单一写入队列、快照序号和仅删除已确认项，或改为后端事件累计。退出时不能只依赖 beforeunload 中未经等待的 Promise，应由后端拥有可持久化的统计生命周期。

### R07 输入清空必须取消旧防抖任务

[appStore.ts](../frontend/src/stores/appStore.ts) 第 42 行防抖工具没有 cancel，clearValue 只重置状态。探针中 setTextValue 后立即 clearValue，80ms 后 value 重新变为旧查询，displayValue 仍为空。快速输入后按 Enter 还可能触发上一轮 value 对应的命令。

同一状态模块中，图片或文件输入后再调用 setTextValue，没有清空 clipboardContentType、files、imageBase64。探针中输入 json 后上下文仍为 image。建议原子更新输入类型与附件，清空、粘贴、触发时取消防抖；最好只对搜索计算防抖，原始输入状态立即更新。

### R08 watcher 退出需要等待生产者停止

[fs_watcher_darwin.go](../internal/command/watcher/fs_watcher_darwin.go) 第 108 行 Stop 关闭 eventCh，第 155 行创建的 AfterFunc 没有被取消或等待。退出后 timer 仍可调用 processEvent；其 select 含向已关闭 channel 发送的分支，即使 ctx 已取消也可能 panic。Go 探针已复现 send on closed channel。Windows 文件存在同样结构。

建议统一管理 timers 与工作 goroutine，Stop 取消任务并 Wait，最后由生产者关闭 channel。验收：收到文件变化后立即退出、定时任务触发期间退出、重复 Start 与 Stop，均无 panic 和泄漏。

### R14 Windows 需要分开保存快捷方式与执行目标

[app_scanner_windows.go](../internal/command/application/app_scanner_windows.go) 第 87 行仅读取 TargetPath、IconLocation、Description，没有 Arguments、WorkingDirectory 等字段；parseShortcut 将 command.Path 改成 TargetPath，源 .lnk 路径丢失。因此需要参数的 Electron 应用、浏览器配置启动、更新器入口等可能启动错误。

源路径丢失也破坏同步：扫描输入是 .lnk，数据库保存的是 .exe；updateApplications 的 seen 检查和 watcher 的删除查找使用不同身份。相同快捷方式可以反复被当作新增，再遇到数据库 path UNIQUE 约束，导致整批新增事务失败；删除 .lnk 时也找不到目标记录。重解析 .exe 还会覆盖从注册表或快捷方式得到的展示名称。

建议模型区分 sourcePath、launchPath、arguments、workingDirectory 与稳定 identity，启动时保留 Windows Shell 快捷方式语义。交叉编译通过不代表此流程正确，需要 Windows 实机验证多快捷方式指向同一 exe、参数启动、安装、删除与改名。

### R23 文件监听应收敛到最终磁盘状态

[app_manager_darwin.go](../internal/command/watcher/app_manager_darwin.go) 第 158 行对同一路径 5 秒内事件直接跳过，而且在处理成功前就 markAsProcessed。一次 Added 后紧接 Removed 或原子替换，最终事件可以被丢掉。底层事件队列满时也直接丢弃。启动后的全量检查只延迟执行一次，长期运行期间没有周期性兜底。

macOS watcher 只监听几个目录，并未订阅每个 bundle 内部；不能保证发现 Info.plist 或资源变更。Windows 递归订阅只在初始化或 AddWatchDir 时执行，新创建的应用目录没有补订阅。

建议按路径合并事件后查询最终磁盘状态，用 dirty 标记驱动同步，并在队列溢出、休眠恢复、错误后触发全量 reconcile。新增目录补订阅。配置中的批处理、去重参数应实际参与实现，避免声明与运行行为分离。

### R24 原生操作需要明确错误返回

[api_darwin.go](../internal/api/api_darwin.go) 第 47 行和 Windows 对应实现仅处理 os.IsNotExist，其他 os.Stat 错误继续调用 stat.IsDir。Go 探针传入超长文件名时触发 nil pointer panic。应对任意 err 直接返回结构化错误。

同一能力链还有以下问题：[command.go](../internal/command/command.go) 的 TriggerCommand 与 coordinator 返回 void，runner 失败仅记录日志，前端仍清空输入并隐藏窗口；InstallPluginByFileDialog 把每个失败记录后继续，最终返回 nil，全部失败时也无法给用户结果；SaveBase64Image 以秒命名且使用可覆盖写入，同秒两次保存可能互相覆盖。

建议能力 API 返回 result 或 error，批量安装返回逐项结果，失败时保留输入并显示可操作提示。图片保存使用独占随机文件名与数据校验。

### R26 热键状态与退出需要可观测

[hotkey_manager.go](../internal/app/hotkey_manager.go) 的 RegisterAll 对注册失败执行 continue，最后始终返回 nil；UpdateHotkey 可以持久化一个不可用配置并报告成功。错误又以 Info 级别记录，而默认日志级别为 error，用户可能没有任何可见提示。

[hotkey.go](../internal/app/hotkey.go) 的 listen 读取 l.hk、l.quit，Unregister 又异步置 nil，没有等待监听 goroutine 退出；存在 race 与空指针风险。WaApp.isHidden 也同时被热键 goroutine 与桥接调用访问。

建议注册失败返回逐项结果，保留可用的旧热键；监听 goroutine 捕获固定 hk 与 quit，使用取消信号与 WaitGroup 完成退出，窗口操作在明确线程或串行队列执行。

### R27 SQLite 参数需要应用到每个连接

[wa_db.go](../pkg/db/wa_db.go) 第 71 行允许 10 个连接，第 83 行通过一次 db.Exec 设置 busy_timeout。busy_timeout 是连接级参数，一次设置不能保证后来新建的连接具有同样配置。在 watcher、插件存储和使用统计共同写入时，可能出现比预期更早的 SQLITE_BUSY。

建议通过驱动 DSN 或连接初始化钩子设置每个连接的参数，并明确读连接与写队列策略。验证多个同时持有的连接的 PRAGMA 值，以及竞争写入时的超时与恢复。数据库错误不应在 GetCommands/GetPlugins 中全部转换成“空列表”，否则数据不可读会被误认为没有安装应用或插件。

## 官方插件功能

### R15 JSON 语法验证不能依赖当前位置解析器

[JSON index.html](../plugins/official/watools.plugin.json/plugin/index.html) 的 JsonTreeParser 对 object 和 array 循环到输入末尾后直接返回，没有强制匹配结束括号；字符串也允许未转义换行。parseJsonText 仅在自定义解析器报错后调用 JSON.parse，因此不会拦截这些输入。

探针确认 `{"a":1,`、`[1,`、包含原始换行的字符串都被接受。随后格式化或压缩会把无效输入转换成另一个合法值，错误地改变用户数据。建议先由严格 JSON parser 验证，再构造位置树；或者直接使用经过验证且带位置信息的解析器。验收应包括截断输入、尾随逗号、控制字符、深层嵌套与大整数精度说明。

### R16 特殊键必须按普通数据处理

同一文件第 541 行使用 `{}` 与 `value[key] = child.value`，`__proto__` 会改变该对象原型并从 JSON 输出中消失。探针将 `{"__proto__":{"hidden":true},"a":1}` 解析后只剩 `{"a":1}`。query 转换第 816 行使用 `key in target`，constructor 和 toString 被误认为已有属性，输出数组混入原型函数，序列化为 null。

这是数据损坏及局部原型行为，探针没有证明全局 Object.prototype 被污染。建议使用 Object.create(null)、自有属性检查或 defineProperty 安全写入。先锁定所有合法 JSON 键可往返的契约，再处理 URL 自动多次解码与数字自动转型是否符合产品预期。

### R17 自动翻译需要保证最后一次输入生效

[翻译 index.html](../plugins/official/watools.plugin.translate/plugin/index.html) 第 492 行在已有请求时直接丢弃普通自动翻译请求。输入修改时既没有更新 latestRequestId，也没有记录待处理的新文本。因此慢请求期间编辑，旧响应仍通过 requestId 检查，最新文本没有后续请求。探针中输入从 old 变成 new，网络调用仍只有一次，输出是 old 的译文。清空输入期间旧响应也可以重新填回译文。

建议输入变化立即使旧请求失效，采用可取消的 latest-wins 队列；旧请求完成后必须处理最新文本。即时快捷键存在输入节点与 window 的重复处理路径，建议只保留一个触发入口或阻止重复传播。

计算器、二维码和字符统计的优化建议见后面的插件本地工作项。本轮没有把计算器的 new Function 直接判为任意代码执行：输入有字符白名单，尚未发现可突破白名单的载荷；应改为数学表达式解析器，以减少 CSP 兼容问题、明确运算语法和处理大数舍入溢出。

## 安全边界与更新

### R10 更新安装必须重新验证下载记录

[update/service.go](../internal/update/service.go) 第 192 行 Install 仅检查路径非空与文件存在，没有确认来自本次可信 manifest、是否位于更新缓存、checksum、安装类型或版本。下载阶段的 SHA256 校验不能保护下载后修改，也不能约束直接调用 InstallUpdateApi 的路径。探针中普通文本文件被 Install 接受，源码运行环境返回 manual；没有执行真实安装。

此外 checksum 为空时下载和缓存校验都直接放行。建议安装接口接受后端生成的 updateId，后端持有可信记录，并在交给安装器前再次检查哈希、平台、版本与包身份。哈希保证内容一致性，不能替代发布者签名；签名、公证及 manifest 签名需要与发布流程一起设计。当前风险需要可访问桥接的代码或本地文件变化，不应描述为已证明的无交互远程安装漏洞。

### R11 macOS 更新不能先删掉唯一可用版本

[install_darwin.go](../internal/update/install_darwin.go) 第 60 行附近生成脚本，sleep 2 后 rm -rf 当前 app，再用 ditto 复制。没有等待进程真实退出、备份、复制失败检查或回滚。复制失败和磁盘空间不足可以留下已被删除的应用，脚本仍尝试清除 quarantine 和打开路径；临时 staging 目录也没有完整清理。

建议在目标卷创建完整新 bundle，验证后等待旧进程退出，再保留旧版本并切换；失败恢复备份。为安装结果设置持久化状态，重启能显示失败原因。应在隔离应用副本中验证退出慢、安装中断、复制失败和重新启动。

### R12 更新文件名与脚本引用需要严格约束

[update/service.go](../internal/update/service.go) 第 318 行的 updateAssetPath 仅清理版本字段，assetName 直接参加 filepath.Join。探针使用 `../../../probe` 得到缓存目录之外的路径。利用需要控制 manifest 内容，目前没有证明网络攻击者可以替换 GitHub HTTPS 返回。

[install_darwin.go](../internal/update/install_darwin.go) 使用 Go `%q` 生成 shell 参数；双引号不能阻止 `$()`、反引号与变量展开。路径含这些合法文件名字符时仍可被 shell 求值，包括当前 app 所在目录或解压后的 bundle 名称。建议脚本通过位置参数接收路径并使用 `"$1"` 等引用，避免插值生成 shell 代码；资源文件名使用 basename 白名单和路径包含关系校验，同时验证解压后的 bundle 身份。

### R13 工具链与开发依赖需要安全升级

[package.json](../frontend/package.json) 固定 Vite 7.1.11，锁文件中的相关依赖被 pnpm audit 命中 16 条公告。Vite 维护者公告确认开发服务器存在文件读取问题，某些攻击要求服务器显式暴露到网络；本仓库 vite.config 没有设置 server.host，因此不能据此断言桌面发布包存在同样暴露。应更新受影响的构建依赖并重新扫描，不要只处理最早一条公告的最低补丁号。参见 [Vite WebSocket 文件读取公告](https://github.com/vitejs/vite/security/advisories/GHSA-p9ff-h696-f583) 与 [Windows 路径检查绕过公告](https://github.com/vitejs/vite/security/advisories/GHSA-fx2h-pf6j-xcff)。

[go.mod](../go.mod) 声明 toolchain go1.26.1。以此工具链进行 govulncheck 得到 14 条标准库符号可达报告，涉及 HTTP、TLS、证书、URL、XML 等。可达不等于每条都能在本产品的调用条件下利用，例如有些条目具有平台或协议限制。已核对的 URL、TLS 和 XML 公告包含 Go 1.26.6 修复；建议至少覆盖扫描列出的全部修复版本，并在实际发布工具链上重新扫描。参见 [Go URL 公告](https://pkg.go.dev/vuln/GO-2026-6218)、[Go TLS 公告](https://pkg.go.dev/vuln/GO-2026-6090)、[Go XML 公告](https://pkg.go.dev/vuln/GO-2026-6088)。完整 ID 与调用链保存在审查证据中。

发布 CI 当前没有独立 PR 检查工作流，也没有在发布前运行 Go 测试、race、audit、govulncheck 或官方插件契约检查。建议新增 macOS 与 Windows 的验证流水线，安全公告按调用环境分级处理；不要将所有扫描结果无差别等同于线上可利用漏洞。

### R19 插件信任模型必须进入 SDK 设计

[wa-plugin.tsx](../frontend/src/components/watools/wa-plugin.tsx) 使用同源、无 sandbox 的 iframe，并注入完整 runtime；[api/plugin.ts](../frontend/src/api/plugin.ts) 在宿主 window 直接执行插件 module。插件可以访问 parent 的 DOM、共享存储与 Go 桥接；Storage API 的 packageId 来自调用参数，[coordinator.go](../internal/coordinator/coordinator.go) 第 302 行之后只检查非空，不能验证实际调用身份。插件路由也不按 enabled 状态授权。

仓库文档已经声明插件是可信代码，所以这属于扩展第三方插件前必须解决的边界设计，不应声称违反了现有沙箱承诺。若继续使用完全可信模型，应明确权限及来源，优先避免非必要敏感数据传播；若要支持受限第三方插件，则应将插件代码移出宿主主线程与同源环境，通过受限 RPC 提供能力，校验调用会话身份、权限和数据范围。

只加一个允许同源的 iframe sandbox 或只给前端 API 包装 packageId 都不能建立该边界。网络域名限制也必须同时考虑原生代理、浏览器 fetch 和资源 CSP，不能只限制其中一条路径。

### R20 密钥与输入应采用不同存储策略

[翻译 index.html](../plugins/official/watools.plugin.translate/plugin/index.html) 第 411 行附近同时将 DeepL key 明文写入 localStorage 和插件数据库；[commandRankingStore.ts](../frontend/src/stores/commandRankingStore.ts) 将完整 normalizedValue 与包含全文的 inputKey 持久化，最近 30 条也可能包括密码、私人文本或完整翻译内容。[plugin-context.ts](../frontend/src/lib/plugin-context.ts) 保存完整剪贴板启动上下文最长 24 小时，成功读取后没有消费删除；[wa-command.tsx](../frontend/src/components/watools/wa-command.tsx) 第 249 行还把剪贴板内容写到 console。

建议将 secret API 与普通 KV 分离，使用系统凭据存储，密钥不进入 GetPlugins 返回的完整 storage；排序历史使用不可还原的输入标识、摘要或明确长度限制，避免保存原文。启动上下文采用会话内短期对象并在结束后清理。共享同源环境下，仅本地加密后仍把解密密钥交给所有插件没有隔离价值。

### R22 HTTP 代理需要取消与配额

[api.go](../internal/api/api.go) 第 89 行的 HTTP 代理允许任意地址、方法和自定义 timeout，响应由 io.ReadAll 无上限读入。没有使用请求 context，插件关闭或宿主退出不取消正在进行的请求。大量或大体积请求可以消耗宿主内存，超大 timeout 还可能溢出 duration。

在完全可信插件模型下，访问 localhost 或内网可能是合法能力，本轮不把它无条件认定为 SSRF 漏洞。如果引入受限插件，应明确域名、私网访问和重定向权限；无论采用哪种模型，都应设置最大响应体、最大超时、并发上限、取消令牌与请求身份。返回二进制数据也应有明确编码契约，当前统一转 string。

## 可观测性与性能

### R28 日志需要真实结构化与有界查询

[pkg/logger/utils.go](../pkg/logger/utils.go) 的 Error 只使用首个字符串，调用处传入的 packageId、file 等键值字段全部被丢弃。日志页虽支持来源和插件过滤，但缺少可靠结构化来源。[conversion.go](../pkg/db/conversion.go) 的存储 JSON 解析失败还会把完整 storage 写入日志，可能包含密钥。

[logger.go](../pkg/logger/logger.go) 只按进程启动当天打开日志文件，没有大小轮转、保留策略或跨午夜切换。[log_query.go](../pkg/logger/log_query.go) 第 105 行先扫描并持有全部匹配记录再排序，limit 只限制最后输出；分页每次重扫，长日志和大范围过滤会持续增加内存与处理时间。建议保留真实结构化字段、统一脱敏，设置滚动与保留上限，再实现有界查询、稳定 cursor 或增量索引。

前端构建实测有 1,588 个文件，dist 约 7 MiB，主 JS 794.29 kB，gzip 281.77 kB。[wa-icon.tsx](../frontend/src/components/watools/wa-icon.tsx) 使用 lucide DynamicIcon，给每个图标生成可动态导入资源。建议宿主常用图标静态注册，插件图标采用受控映射或 SVG 资源协议，并做路由级懒加载。当前 vite.config 通过提高告警阈值接受包体，不等于已验证启动与 WebView 解析成本。

插件性能方面，启动时并行 import 所有启用插件，再对 UI entry 发 HEAD；没有单插件超时、有限并发或导入顶层 await 的处理。某个永不完成的导入会让 Promise.all 一直等待。match 同步执行在 React 主线程，try/catch 只能处理异常，不能限制无限循环或慢运算。plugin-item 还重复线性 find，排序比较每次重新计算历史分数，再在宿主重复排序。建议声明式触发规则、隔离运行、性能预算、预计算分数和 packageId 索引；这些是明确的结构性优化点，尚未测量实际输入延迟。

图标缓存只按源路径生成 key，不包含修改时间，应用升级后可能继续显示旧图标；同图标并发生成缺少去重与原子提交。JSON 插件自带 Monaco 目录约 15 MiB，应记录版本与来源、裁剪无关语言和 worker，并将第三方离线资源纳入 SBOM 与更新检查。

建议分为五个可独立验证的工作阶段。前两个阶段先固定数据与 SDK 契约，后续性能工作基于稳定机制进行。

| 阶段 | 工作范围 | 完成条件 |
| --- | --- | --- |
| 1 数据与可靠性修复 | R01、R04、R05、R07、R08、R10、R11、R13、R24 | 插件升级不丢数据；统计可跨重启保留；退出无 channel panic；更新校验与失败恢复有证据 |
| 2 插件运行时与加载 | R02、R03、R09、R18、R19、R21 | 版本化资源、逐插件状态、单插件失败隔离、启停与 dispose、固定启动上下文、明确可信边界 |
| 3 插件本地能力 | R15、R16、R17、R20，以及共享 SDK | JSON 严格往返；翻译最后输入生效；密钥不进入普通 KV；存储迁移、取消和错误有统一契约 |
| 4 平台能力与持久化 | R06、R14、R22、R23、R25、R26、R27 | 两平台能力矩阵、原生剪贴板与应用启动、稳定 watcher 同步、连接参数与数据目录迁移 |

### 插件加载机制优化项

将发现与执行分开：后端输出经验证的 manifest 索引，前端先获得可显示、可管理的条目，用户触发时再激活对应运行时。manifest 增加 schemaVersion、minHostVersion、稳定 entryId、声明式触发器、能力声明与 storageSchemaVersion。对旧版函数式 match 保留明确的兼容路径。

PluginManager 统一管理版本、加载状态、失败原因、active session 和 dispose。模块 URL 按内容版本不可变；升级在完成准备后切换。避免将 scoped API 临时挂到全局 window.watools：两个 executable 异步重叠会串包，结束顺序还可能恢复错误实例。将 api 作为执行上下文显式传入，或通过有身份的 RPC 提供。

最低回归场景：禁用启动后启用、导入异常与超时、坏 manifest、同版本重装、相对依赖更新、两个命令并发执行、关闭后取消任务、宿主升级后的旧插件兼容。

### 插件本地优化项

统一官方插件的宿主握手、快捷键、错误显示、存储、下载与剪贴板助手，减少每个 index.html 重复实现初始化与重试。建立可独立导入的功能核心，把 JSON 转换、文本统计、数学计算等从大 HTML 内联脚本中移出。

JSON 优先修严格语法与特殊键，再处理数字精度、深层嵌套和大文本 worker。翻译优先修请求队列、清空输入失效、凭据存储和失败重试。计算器应使用明确数学语法的 parser，并定义大数与舍入精度。二维码对超大图片先缩放或在 worker 识别，明确内存与长度限制。字符统计应明确 UTF-16 code unit、Unicode code point 和 grapheme 的用户口径，测试 emoji、组合字符与换行。

每个官方插件提供最小 fixture 集与 manifest 契约检查，打包时验证资源存在、入口唯一、依赖完全离线。插件包生成应检查 zipWriter.Close 和输出文件 Close 的错误，当前 pluginctl 通过 defer 忽略结尾写入失败。

### 平台能力优化项

定义平台适配接口与 capability 查询，分别表达支持、授权不足、环境不可用与执行失败。UI 只展示当前平台可用能力，并能解释权限或环境问题。Windows 的剪贴板和扫描当前频繁启动 PowerShell，建议采用原生 API 或批量读取；clipboard 检测应依据真实内容，单元素 JSON 输出与空返回值也应加入 Windows 用例。

应用索引分开保存发现源、执行信息和展示元数据。锁定扫描目录与用户自定义目录规则，确保 watcher、扫描和数据库使用同一身份。在 macOS 与 Windows 验证多屏缩放、较小屏幕和窗口高度：当前固定管理页高度 760px，窗口宽度最小值 840px，存在超出小屏可用工作区的风险；应根据实际工作区限制尺寸。

### 性能验收基线

在正式优化前记录冷启动首屏、插件索引就绪、首次打开每个 UI 插件、输入到结果更新的 p50 与 p95、空闲与多次开关插件后的内存、扫描时间与原生子进程次数。使用 10、50、200 插件，短输入、长剪贴板、大图片和大 JSON 等固定 fixture。

建议先把搜索与 match 的 p95、启动时间和会话内存增长作为预算，具体阈值由基线和产品体验决定。无需先改框架；主要收益来自减少启动执行、固定生命周期、降低数据复制、预计算检索与排序、受控加载资源。
