# 自动呼出剪贴板与插件启动性能调研

[返回文档索引](../README.md) · [复现材料](../reviews/evidence/2026-10-06/README.md)

调研日期：2026-10-06。源码基线：`2c6a229`。范围是当前 macOS 呼出时自动带入剪贴板、show 和 origin 分离、搜索匹配及插件启动上下文。本轮完成源码检查和合成数据探针，未修改功能实现，未进行原生 GUI 验收。

本文保留优化前的调研结论。随后用户授权完整实施；现状与实现范围见 [实现机制](../architecture/implementation-mechanism.md#剪贴板原文与呼出性能)，优化后的检查和原生结果见 [同日证据索引](../reviews/evidence/2026-10-06/README.md)。

结论：现有分离只约束输入框显示，没有约束搜索计算。完整原文进入三类 Fuse 搜索和同步插件 matcher；已在独立 Node 进程复现秒级阻塞。优先让搜索有明确长度和来源边界，同时保证 origin 原样保存。插件的 launchId 和内存交付方式可以保留，移除 JSON 深拷贝、避免统计落盘阻塞打开即可先取得实际改善。原生读取与 WebKit 桥接的贡献仍需单独测量。

## 当前调用链

1. 全局快捷键通过 `HotkeyManager` 调用 `WaApp.ShowApp()`，显示并激活窗口。这一步没有主动读取剪贴板。
2. `WaCommand` 的 window focus 监听调用 `GetClipboardContentApi()`；macOS 检测类型并读取所有可用文本、图片和文件，完整数据通过 Wails 返回前端。
3. 仅当主类型是文本时，自动呼出走 `setValueAuto`。现有 `inputRevision` 能阻止清空或新输入之前发出的读取覆盖当前输入，但读取已发生，即使已有内容也仍然请求剪贴板。
4. `appStore.value` 相当于 origin，`displayValue` 相当于 show。自动带入超过 2000 个 UTF-16 code unit 的文本时，show 变成首尾各 30 个 code unit 加省略标记，总长 70。
5. `WaCommand` 用完整 `value` 构造排名上下文，将它送入应用、系统操作、内置功能的 Fuse 搜索，并传给所有启用插件的 `match(context)`。这些操作都在前端主线程同步执行。
6. 选择 UI 插件先等待使用统计更新，再把 `PluginContext` 序列化并解析成启动快照，Map 用 launchId 保存。路由只带 packageId、file、launchId；iframe URL 不带正文。
7. iframe load 后直接注入 `pluginContext`、兼容字段 `inputValue` 和宿主 API，派发 `watools:context-ready`，释放 Map 记录并清空启动器输入。Executable 插件直接接收 context，并串行运行以兼容全局 API。

主要源码入口：[`appStore.ts`](../../frontend/src/stores/appStore.ts)、[`wa-command.tsx`](../../frontend/src/components/watools/wa-command.tsx)、[`wa-plugin-item.tsx`](../../frontend/src/components/watools/wa-plugin-item.tsx)、[`plugin-context.ts`](../../frontend/src/lib/plugin-context.ts)、[`wa-plugin.tsx`](../../frontend/src/components/watools/wa-plugin.tsx)、[`app_darwin.go`](../../internal/app/app_darwin.go)。

## 已复现的性能问题

环境：Apple M5、arm64、Node 24.11.0、当前安装的 Fuse 7.1.0。每行是独立进程中一次操作的耗时，准备模块和测试数据在计时外；不是多次采样的中位数。完整搜索使用 100 个合成应用及仓库实际的四字段配置。子进程有 5 秒总超时，包含进程启动和准备；超时只表示该进程未在预算内完成，不冒充精确操作耗时。

| 操作 | 合成文本 | 结果 |
| --- | --- | --- |
| 扩展查询解析，应用列表为空 | 2 万字符，多词文本 | 62.2 ms |
| 扩展查询解析，应用列表为空 | 10 万字符，多词文本 | 1611.1 ms |
| 扩展查询解析，应用列表为空 | 10 万字符，带引号和空格的 JSON 片段 | 3708.2 ms |
| 扩展查询解析，应用列表为空 | 100 万字符，多词文本或 JSON 片段 | 子进程 5 秒超时 |
| 应用搜索 | 10 万字符，多词文本 | 1623.4 ms |
| 应用搜索 | 10 万字符，无空格文本 | 2830.0 ms |
| 应用搜索 | 100 万字符，多词或无空格文本 | 子进程 5 秒超时 |
| 应用搜索，关闭扩展查询 | 10 万字符，多词文本 | 3250.3 ms |
| 应用搜索，只取 128 字符作为实验查询 | 原始文本 2 千至 100 万字符 | 1.5 至 1.6 ms |
| 全文排名规范化 | 100 万／1000 万字符 | 8.7／110.2 ms |
| 六个官方插件的全部 matcher | 100 万／1000 万字符，多词文本 | 12.1／143.3 ms |
| 当前 JSON 启动快照 | 100 万／1000 万字符 | 1.9／17.4 ms |
| 复制对象外壳并共享字符串的实验快照 | 100 万／1000 万字符 | 约 0.01 ms |

Fuse 7.1.0 的本地 `dist/fuse.mjs` 中，`parseQuery` 用带后缀引号检查的正则拆分空格，每个候选分隔位置可能再次扫描剩余查询。多词文本长度增加十倍时，本次解析耗时增加约 26 倍；这与超线性的重复扫描相符。无空格长串虽然解析较快，Bitap 仍将查询拆成多个 32 字符 chunk，对每个候选字段遍历所有 chunk，所以也会阻塞。

三个 Fuse 实例均启用了扩展查询，会分别构造查询。`limit: 5/10` 在当前 Fuse 版本中是在匹配后裁剪结果，并不限制查询解析或候选扫描成本。仅关闭 `useExtendedSearch`、只调小结果数、增加 debounce，都无法建立长文本处理的计算上限。[Fuse 官方扩展查询说明](https://www.fusejs.io/extended-search.html)解释了空格、引号与管道的特殊含义；具体性能结论依据仓库安装的 7.1.0 源码和本次探针，不能把官网新版本行为直接当作现状。

这些结果证明了当前呼出链路中确实存在足以解释卡顿的同步阻塞点。尚未测量用户实际剪贴板、当前安装的第三方插件、WebKit、原生剪贴板供应方及 Wails 传输，因此不把数字解释为实机呼出总耗时。

## show 和 origin 的正确性问题

| 当前行为 | 影响 | 建议 |
| --- | --- | --- |
| 自动带入经过 `value.trim()`，手动粘贴保留原文 | origin 不保真，缩进和结尾换行丢失，两条入口语义不同 | 所有剪贴板入口原样存 origin；trim 仅用于派生查询或空白判断 |
| 只对 `isAuto` 的长文本生成摘要 | 手动粘贴把完整长文本交给 input 和 cmdk | 统一摘要生成规则，与自动／手动入口解耦 |
| 80 万字符以上跳过相同文本判断 | 同一超长剪贴板清空后再次呼出仍触发重处理 | 用剪贴板版本识别重复读取，并明确重复内容带入策略 |
| 先用未 trim 的内容比对 `lastCopiedValue`，再保存 trim 后的内容 | 带边缘空白的同一文本也可能绕过去重 | 去重标识和 origin 保存规则保持一致 |
| 摘要仍是可编辑 input，`onValueChange` 直接替换 value | 在摘要中追加字符会把百万字符 origin 替换为约 71 字符的摘要衍生内容 | 明确摘要展示与新查询输入的关系；原文编辑应打开完整编辑器 |

摘要编辑的探针验证了状态转换，未验证物理输入。自动带入后原有全选再打字可以是合理的“替换输入”交互；问题是当前没有明确区分这种替换与“编辑原文”。`compressedDisplay` 已记录在 store，但组件没有用它建立该边界。默认在输入框中复制选中内容也会复制 show，若需要复制 origin，应提供明确动作。

## 插件启动传递可以保留的部分

当前 launchId 加内存 Map 避免把正文放入 URL 或 sessionStorage；iframe 与宿主同源，可以直接赋值上下文对象。这里没有第二次经过 Go，也没有 `postMessage` 序列化。`input.value` 和 `clipboard.text` 在普通对象中可以共享字符串；重复字段不意味着必须复制正文。

JSON 深拷贝才会将同一文本在两个字段中分别编码，再解析回来。PluginContext 是已知结构，包含对象外壳、字符串和文件路径数组。可复制 `input`、`clipboard` 的对象外壳及 `files` 数组，共享不可变字符串，继续满足现有“原对象修改不影响启动快照”的回归约束。直接保存可变的原 context 引用会破坏该约束，不能作为优化替代。

`onTriggerPluginCommand` 会等待 `updatePluginUsage`，而其内部实际等待立即落盘，并非注释所说的 debounce。应先创建固定启动快照、交付插件，再让使用统计按既有失败重试机制后台提交；停用检查、启动错误和 usage 时机仍须保持正确。usage 更新也会改变 plugins 数组，从而让 matcher 重新运行，宜拆分入口集合和统计排序的缓存依赖。

建议将启动记录生命周期显式建模，取代依赖 `useMemo` 故意遗漏 liveContext 来“固定快照”的写法。cleanup 应跟随实际 launchId，失败、取消、路由参数切换和卸载均释放记录。目前 20 条与 5 分钟限制只在相关操作时执行，不能约束总字节数，也不是定时回收。以后引入大型附件时，应增加总量预算和主动释放。

## 建议的重构顺序

### 先约束搜索并保证原文完整

保留现有 `value` 和插件上下文契约，增加专门派生的 searchQuery：短输入维持现有搜索，长剪贴板不作为应用、系统操作、内置功能的模糊查询，排名按来源和内容类型处理。搜索长度上限应集中定义，并在 store 搜索边界与各入口执行前检查，避免其他调用方再次把全文送入 Fuse。

128 字符只是本次实验参数，2000 字符只是现有显示阈值，两者都不是已经确定的产品参数。最终边界应兼顾正常应用搜索、显式命令与性能验收；show 的首尾摘要也不应直接成为 searchQuery，否则摘要尾部和省略号会参与搜索。

同时统一自动带入和粘贴的 origin 保存、show 派生、revision 校验与清空逻辑，移除自动带入的 trim。插件启动采用类型明确的快照，去掉 JSON 编解码和使用统计的等待。保留插件收到原文、路径数组独立、图片数据完整的兼容约束。

### 再约束自动匹配和剪贴板读取

插件 matcher 当前在 React 渲染中执行所有启用入口，之后才裁剪前三个结果；try/catch 只能捕获异常，无法中断计算。短期优先为官方插件增加明确的廉价匹配规则和长度边界，昂贵解析放到真正打开或执行之后。第三方旧 matcher 不能偷偷改为只收到截断文本，否则匹配语义会变。

后续应落实已有 [插件加载与 SDK 目标](../backlog/plugin-loading-and-sdk.md)：manifest 声明关键词和支持的内容类型，主线程只匹配小查询和元信息；需要全文分析的匹配放入可终止 Worker。Worker 需要加载可独立运行的模块，无法把任意闭包直接搬过去；依赖 DOM 的旧插件应保留明确兼容路径。对于长输入，提供无需执行旧 matcher 的显式插件打开方式，才能给宿主主线程建立可靠的上限。Promise 包装或定时器不能中断同步 matcher。

当前自动呼出只使用文本，却读取全部可用格式。建议区分自动文本带入和显式粘贴完整素材的读取用途：已有输入时提前跳过请求，合并并发 focus 请求，失败显式处理；读取类型与所需内容尽量在一次 AppKit 调度中完成，并检查读取前后的剪贴板版本，防止混合不同版本的数据。保留现有原生线程要求，不能直接把 NSPasteboard 访问搬到 Go 后台线程。

macOS 可用 `NSPasteboard.changeCount` 作为剪贴板所有权版本，重复 focus 时优先检查版本并复用快照。它不是内容哈希；需要定义复制同样内容但版本变化的语义、异常供应方的失效策略和缓存回收。[Apple changeCount 文档](https://developer.apple.com/documentation/appkit/nspasteboard/changecount?changes=_5)描述的是所有权变化，不应承诺能覆盖任意原地内容修改。Windows 后续保留等价接口和平台实现，本轮不把其兼容验收混入 macOS 调研。

### 桥接仍是瓶颈时再引入原文引用

若实机计时显示首次全文读取及 Wails 编解码仍明显拖慢呼出，可将自动响应改为小型 show、类型、长度及 snapshotId，origin 保存在宿主内存中，插件实际需要时按 id 读取固定快照。该方案能减少自动呼出阶段的桥接体积，但首次取得 show 仍可能让剪贴板供应方生成全文，不能保证原生读取变成常数时间。

快照必须绑定一次读取，插件打开时不能重新读取当前剪贴板代替旧 origin；版本变化、过期与释放应明确返回状态。仅查类型时可暂不取正文并先完成窗口显示，但随后原生内容读取是否阻塞 AppKit 仍需实机验证。这项改造会涉及 AppService、生成绑定、HostAPI、mock 和插件协议，建议在前述低成本修复后根据数据决定，避免同时维持前后端两套完整原文。

若进一步将“输入命令”和“剪贴板素材”分成独立状态，必须明确 `input.value` 与 `clipboard.text` 的契约并迁移官方插件：目前两者在剪贴板文本场景是同一原文，不能在兼容旧 matcher 时突然把前者改成摘要或短命令。这属于后续协议设计，不是本次已实施能力。

## 后续验收范围

使用隔离开发数据验证 2 千、2 万、10 万、100 万和 1000 万字符的多词文本、无空格文本、合法及不完整 JSON、Unicode 和边缘空白。分别记录 focus 到首帧／可输入、原生读取、桥接、排名、搜索、每个 matcher、快照、iframe ready 和插件首次渲染；日志只记长度、类型、版本和耗时。

必须确认自动带入和手动粘贴保留完全相同的 origin，show 有界；没有全文进入通用搜索与排名；重复呼出、复制同内容、读取期间打字或清空、取消启动和路由切换行为正确。插件接收的原文和文件数组不因清空启动器而变化；已有启动快照回归和六个官方插件继续可用。具体响应时间门槛应由原生基线确定，不把本次 Node 数字直接作为 GUI 指标。

本次基线前端回归 18 项通过。未运行 Go 全量检查和 GUI 验收，因为没有修改实现；当前超长文本卡顿仍未修复。
